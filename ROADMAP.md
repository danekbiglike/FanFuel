# ROADMAP.md

Roadmap описывает поэтапное развитие FanFuel. Версии до `v1.0` предназначены для controlled launch и публичной беты, а не для полной зрелости платформы.

## Принципы roadmap

- Сначала веб-платформа, затем mobile-first PWA, затем нативные приложения.
- Сначала mock-провайдеры платежей и выплат, затем реальные интеграции.
- Сначала юридически менее рискованные категории: creator assets, OBS-паки, дизайн-ассеты, коучинг, цифровые услуги.
- Аккаунты, ключи, пополнения и внутриигровые товары не входят в MVP и требуют отдельной юридической и платёжной проверки.
- Любая функция, связанная с деньгами, должна проходить через payment provider abstraction.

## Текущий практический фокус

`v0.3 Marketplace MVP` реализован локально, но перед расширением в `v0.4` нужно стабилизировать текущий слой:

1. Провести ручной browser smoke для buyer/seller/admin marketplace flow: товар, checkout, mock payment, safe deal actions, review, admin moderation.
2. Добавить automated tests для order/mock safe deal transitions, idempotency, permission checks и базового UI smoke.
3. Разделить перегруженный `/me/profile`: оставить account/settings, а Studio goals/widgets вынести в отдельный role-aware dashboard.
4. Решить судьбу `FF-0105` upload avatar/banner: сделать до Creator Store или явно перенести в storage milestone.
5. Двигаться к `v0.4 Creator Store + Partners` только после фиксации результатов проверок в `docs/HANDOFF.md`.

Стоп-линия: реальные платежи, выплаты, refunds, ledger, disputes, fiscalization и production safe deal не подключать без `docs/PAYMENTS.md`, provider/legal review, API/domain docs и ADR.

## v0.0 — Foundation

Цель: подготовить техническую основу, структуру и документацию для разработки без хаоса.

Статус: implemented.

Входит:

- структура monorepo;
- Docker Compose для локальной разработки;
- базовые контейнеры PostgreSQL и Redis;
- директория миграций;
- базовый UI kit skeleton;
- i18n skeleton с `ru` и `en`;
- базовые docs;
- healthchecks;
- шаблоны `.env.example`, `SECRETS.template.md`, `docs/SERVER_ACCESS.template.md`.

Не входит:

- production-код платежей;
- реальные кабинеты;
- реальные выплаты;
- публичный запуск.

Критерии готовности:

- разработчик может поднять dev окружение;
- структура пакетов и сервисов зафиксирована;
- документация описывает первые задачи;
- секреты не попадают в Git.

Риски:

- чрезмерное усложнение до появления MVP;
- отсутствие единого формата задач;
- смешивание платежной логики с доменом.

Зависимости:

- финальный выбор package manager;
- базовый Docker Compose;
- решение по auth policy.

## v0.1 — Auth + Profiles

Статус: `implemented`.

Цель: создать базовую модель пользователей и публичных профилей.

Входит:

- регистрация;
- логин;
- роли `buyer`, `streamer`, `seller`, `admin`;
- профили покупателя, стримера и продавца;
- публичная страница автора;
- базовая админка для просмотра пользователей;
- начальная permission model.

Не входит:

- OAuth как обязательная функция;
- сложная KYC-верификация;
- реальные платежи;
- полноценная модерация продавцов.

Критерии готовности:

- пользователь может зарегистрироваться и войти через web UI и REST API;
- роли назначаются на backend, публичная регистрация не выдаёт `admin`;
- публичный профиль автора доступен по slug;
- админ видит список пользователей и может менять статус;
- миграция `000002_auth_profiles` применима локально и на VM.

Риски:

- неправильная модель ролей усложнит будущие права;
- слабая session/JWT policy приведёт к проблемам безопасности.

Зависимости:

- базовая БД;
- миграции;
- i18n для auth ошибок и UI.

## v0.2 — Donate MVP

Статус: `implemented`.

Цель: запустить минимальный поток доната с mock payment и OBS alert.

Входит:

- донат-страница автора;
- создание доната;
- тестовая оплата через mock provider;
- OBS alert widget;
- WebSocket event delivery;
- история донатов;
- цель сбора;
- топ донатеров.

Не входит:

- реальные платежи;
- фискализация;
- кастомный дизайнер алертов;
- расширенная аналитика.

Критерии готовности:

- донат создаётся и проходит через mock payment;
- OBS widget получает событие через WebSocket;
- цель сбора обновляется после успешного доната;
- повторные webhooks не дублируют донат.

Риски:

- потеря realtime-событий;
- отсутствие idempotency;
- небезопасные widget tokens.

Зависимости:

- auth/profiles;
- WebSocket gateway skeleton;
- mock payment adapter.

## v0.3 — Marketplace MVP

Статус: `implemented` для mock/local MVP.

Цель: дать продавцам возможность публиковать товары, а покупателям — оформлять заказы через mock safe deal.

Входит:

- категории;
- товары;
- карточка товара;
- seller profile;
- покупка товара;
- order lifecycle;
- mock safe deal;
- отзывы;
- базовая модерация товаров.

Не входит:

- рискованные категории;
- автоматическая выдача сложных цифровых товаров;
- реальные выплаты;
- сложная рекламная биржа.

Критерии готовности:

- продавец создаёт товар;
- покупатель оформляет заказ;
- оплата проходит через mock provider;
- заказ получает безопасные статусы;
- админ может скрыть товар.

Риски:

- смешивание order/deal/payment статусов;
- хранение файлов без access control;
- некорректная комиссия платформы.

Зависимости:

- S3/R2 abstraction;
- базовая модерация;
- payments skeleton.

## v0.4 — Creator Store + Partners

Цель: связать маркетплейс с витриной автора и партнёрской атрибуцией.

Входит:

- витрина стримера;
- добавление товаров в витрину;
- промокоды;
- партнёрский процент;
- отслеживание продаж;
- аналитика для стримера и продавца;
- отображение доли автора для покупателя.

Не входит:

- сложный recommendation engine;
- многоуровневая партнёрская сеть;
- рекламный кабинет.

Критерии готовности:

- автор добавляет партнёрский товар в витрину;
- покупка корректно создаёт attribution;
- промокод влияет на цену по правилам;
- продавец видит продажи от авторов.

Риски:

- непрозрачная атрибуция;
- конфликт промокодов;
- некорректный расчёт доли автора.

Зависимости:

- Marketplace MVP;
- balance transaction model;
- API analytics endpoints.

## v0.5 — Real Payment Provider Integration

Цель: подключить реального платёжного провайдера через абстракцию без привязки домена к одному оператору.

Входит:

- payment provider abstraction;
- tome adapter, если tome подходит после проверки;
- альтернативный adapter для ЮKassa/ЮMoney или mock;
- webhooks;
- idempotency;
- refunds;
- payouts;
- safe deal lifecycle.

Не входит:

- финальная юридическая модель без внешней проверки;
- production rollout для всех продавцов;
- рискованные категории.

Критерии готовности:

- все платежи идут через `PaymentProvider`;
- provider statuses маппятся в provider-agnostic statuses;
- webhook signature verification реализована;
- retries безопасны;
- операции аудируются.

Риски:

- провайдер не поддержит нужный safe deal/payout flow;
- требования 54-ФЗ/115-ФЗ окажутся сложнее ожидаемых;
- provider lock-in.

Зависимости:

- юридическая проверка;
- договорённость с провайдером;
- staging credentials.

## v0.6 — Seller Balance + Payouts

Цель: добавить внутренний баланс продавца и управляемый lifecycle выплат.

Входит:

- `frozen balance`;
- `available balance`;
- payout requests;
- payout statuses;
- лимиты;
- manual review;
- audit log;
- базовая отчётность;
- режимы Seller Lite и Seller Pro.

Не входит:

- позиционирование баланса как банковского счёта;
- автоматическое налоговое консультирование;
- мгновенные выплаты всем продавцам.

Критерии готовности:

- финансовые движения отражаются через `balance_transactions`;
- available balance не может стать отрицательным;
- payout request проходит статусы;
- админ может отправить выплату на ручную проверку.

Риски:

- юридическая трактовка внутреннего баланса;
- расхождение ledger и provider statuses;
- мошеннические продавцы.

Зависимости:

- real/mock payout adapter;
- audit log;
- provider payout capabilities.

## v0.7 — Disputes + Arbitration

Цель: реализовать понятный и управляемый процесс споров.

Входит:

- открытие спора;
- доказательства;
- сообщения в споре;
- решения админа;
- возвраты;
- удержания;
- рейтинг риска.

Не входит:

- автоматическое юридическое решение;
- сложная медиация;
- ML-антифрод.

Критерии готовности:

- покупатель может открыть спор в допустимый срок;
- продавец получает уведомление и срок ответа;
- админ фиксирует решение;
- refund/hold/payout отражаются в ledger;
- все действия пишутся в audit log.

Риски:

- спорные правила возвратов для цифровых товаров;
- недостаток доказательств;
- ручная нагрузка на админов.

Зависимости:

- SafeDeal lifecycle;
- file evidence storage;
- notification system.

## v0.8 — Anti-fraud + Verification

Цель: снизить операционные и платёжные риски перед публичной бетой.

Входит:

- лимиты для Seller Lite;
- Seller Pro verification;
- risk flags;
- suspicious activity;
- audit logs;
- admin review queue;
- hold policy.

Не входит:

- advanced anti-fraud ML;
- автоматическая KYC-проверка без провайдера;
- скоринг как финальное юридическое решение.

Критерии готовности:

- риск-флаги создаются по событиям;
- лимиты применяются на уровне API;
- Seller Pro проходит проверяемый workflow;
- админ видит очередь review.

Риски:

- ложные срабатывания;
- недостаточные данные для проверки;
- блокировка честных продавцов.

Зависимости:

- seller balance;
- admin tooling;
- юридическая проверка лимитов.

## v0.9 — Mobile Web / PWA

Цель: подготовить mobile-first опыт без нативного приложения.

Входит:

- mobile-first интерфейс;
- PWA;
- push strategy;
- адаптация кабинетов;
- улучшение UX для покупателей и продавцов;
- установка на домашний экран.

Не входит:

- iOS/Android native apps;
- глубокая офлайн-работа;
- сложная mobile analytics stack.

Критерии готовности:

- ключевые сценарии проходят на телефоне;
- PWA manifest и service worker настроены;
- пуши описаны юридически и технически;
- checkout, order и dispute удобно работают на mobile.

Риски:

- push-уведомления требуют согласий и юридической проверки;
- интерфейс кабинетов может стать перегруженным;
- разные ограничения браузеров.

Зависимости:

- стабильный web UX;
- notification model;
- i18n formatting.

## v1.0 — Public Beta

Цель: controlled launch с реальными пользователями и ограниченным набором категорий.

Входит:

- production deployment;
- monitoring;
- backups;
- legal docs placeholders;
- support workflows;
- first real categories;
- controlled launch;
- onboarding продавцов и стримеров;
- операционные инструкции.

Не входит:

- масштабные микросервисы;
- нативные приложения;
- рискованные категории без проверки;
- fully automated arbitration.

Критерии готовности:

- production окружение развёрнуто;
- мониторинг и backups проверены восстановлением;
- support и moderation workflows описаны;
- реальные платежи разрешены только для проверенного scope;
- есть rollback plan.

Риски:

- недостаточная поддержка пользователей;
- юридические ограничения по категориям;
- рост споров после старта.

Зависимости:

- legal review;
- provider contracts;
- production observability;
- ручная операционная команда.
