# UX Rules

Правила UX FanFuel. Они дополняют `docs/UI_RULES.md`, `docs/DESIGN_SYSTEM.md` и `docs/UX_WRITING.md`.

## Общие правила

- Сначала ясность, потом красота.
- Пользователь всегда должен понимать следующий шаг.
- Финансовые действия требуют подтверждения.
- Опасные действия требуют подтверждения.
- Не перегружать экран данными "для солидности".
- Не использовать агрессивную рекламу.
- Не говорить о зрителях как о ресурсе или кошельке.
- Safe deal объяснять человеческим языком как процесс, а не как абсолютную гарантию.
- Статус нельзя передавать только цветом.
- Все пользовательские тексты через i18n.
- Все спорные юридические формулировки помечать `LEGAL_REVIEW_REQUIRED`.

## Покупки

- Цена должна быть видна до главного CTA.
- Валюта форматируется shared helper.
- Условия выполнения должны быть понятны до оплаты.
- Продавец должен быть виден рядом с товаром.
- Safe deal должен быть объяснён до оплаты.
- CTA покупки должен быть один главный в локальном контексте.
- Промокод должен применяться понятно: скидка, причина отказа, срок действия.
- Вклад в поддержку автора должен быть прозрачен и не манипулятивен.
- Нельзя скрывать важные условия в мелком тексте.
- Нельзя открывать рискованные категории без legal/payment review.

## Донаты

- Донат должен отправляться быстро.
- Сумма, валюта, имя и сообщение должны быть понятны.
- Анонимность должна объяснять, что скрыто публично, но не от админов.
- Алерт должен иметь preview в Studio.
- Цель сбора должна иметь прогресс, сумму и валюту.
- Ошибки оплаты должны быть человеческими.
- Mock payment нельзя маскировать под production provider.
- После успешного доната пользователь видит статус и понятное завершение.

## Споры

- Пользователь должен понимать сроки.
- Пользователь должен видеть статус спора.
- Нужно объяснять, какие доказательства нужны.
- Не использовать обвинительный тон.
- Решение админа должно быть понятно.
- Evidence private by default.
- Все действия, влияющие на деньги, должны быть auditable.
- Формулировки возврата по цифровым товарам требуют `LEGAL_REVIEW_REQUIRED`.

## Выплаты

- Показывать доступный баланс.
- Показывать замороженный баланс.
- Показывать pending payout.
- Объяснять холд.
- Показывать комиссии, если они известны и approved для показа.
- Показывать сроки без обещания мгновенности.
- Показывать статус выплаты.
- Не называть внутренний баланс банковским счётом.
- Не показывать кнопку выплаты, если payout provider/domain не готовы.
- Любое действие выплаты требует confirmation и audit.

## Кабинеты

- Dashboard должен начинаться с главных действий.
- Не перегружать статистикой.
- Показывать задачи, требующие внимания.
- Использовать panels/cards только там, где они помогают сканировать.
- Важные статусы должны быть заметны.
- Один пользователь может иметь несколько ролей; переключение ролей должно быть явным.
- Не смешивать Buyer, Studio, Seller и Admin flows в одной длинной странице.
- На mobile таблицы превращать в summary cards.

## Admin UX

- Admin screen показывает next action, а не только data dump.
- Опасные действия требуют confirmation с понятными последствиями.
- Audit-relevant действия должны иметь ссылку или указание, что запись будет создана.
- Не показывать raw secrets, passwords, provider tokens.
- Не делать bulk destructive actions без отдельного spec.
- Support/moderator roles должны видеть меньше, чем admin.

## Marketplace UX

- Карточка товара показывает: название, цену, продавца, формат, safe deal, рейтинг/отзывы.
- Фильтры на mobile открываются как drawer или отдельная зона, не ломая grid.
- Empty state должен помогать изменить фильтр или категорию.
- Не показывать fake products.
- Партнёрские товары автора должны иметь disclosure.

## Widget UX

- Widget read-only.
- OBS URL не должен позволять менять настройки.
- Token visible once.
- Reconnect status должен быть понятен, но не мешать трансляции.
- Preview в Studio должен использовать mock events, а не реальные token.
- Анимации должны уважать `prefers-reduced-motion`.

## Mobile UX

- Mobile не вторичен.
- Длинные русские строки проверять на 320-390px ширине.
- Кнопки не должны ужиматься ниже читаемой ширины.
- Формы идут одной колонкой.
- Financial summaries должны быть видны до CTA.
- Нельзя прятать safe deal conditions ниже оплаты.

## Что нельзя делать

- Нельзя создавать FUTURE/DO_NOT_BUILD_YET pages без изменения статуса в tracker.
- Нельзя добавлять пользовательский текст без i18n.
- Нельзя добавлять реальные платежи без payment/legal review.
- Нельзя заменять пустое состояние маркетинговым обещанием.
- Нельзя делать крупный UI refactor без связи с task/spec.
