# I18N.md

## Цель

FanFuel начинается как русскоязычный продукт, но архитектура должна поддерживать английский язык и будущие локали без переписывания компонентов.

## Базовые правила

- Default locale: `ru`.
- Supported locales на старте: `ru`, `en`.
- Runtime/build-time locale берётся из `NEXT_PUBLIC_DEFAULT_LOCALE` для Next.js и `VITE_DEFAULT_LOCALE` для Vite apps; fallback идёт через общий `resolveLocale`.
- Пользовательские тексты нельзя хардкодить в компонентах.
- Валюту нельзя хардкодить.
- Форматы дат, чисел, валют и относительного времени должны зависеть от локали.
- Юридические тексты нельзя хранить в коде компонентов.
- Тексты лендинга, ошибок, писем и уведомлений выносятся в словари или шаблоны.

## Naming keys

Ключи должны быть стабильными:

```txt
auth.login.title
auth.login.submit
marketplace.product.buyButton
payments.status.awaitingPayment
errors.validation.required
notifications.order.statusChanged
```

Запрещено использовать текст как ключ:

```txt
"Войти": "Войти"
```

## Правила для компонентов

- Компонент получает готовую функцию перевода или использует локальный hook.
- Строки UI, placeholders, labels, tooltips, aria-labels и toast messages идут через i18n.
- Нельзя вызывать `getDictionary("ru")` напрямую в компонентах; использовать общий helper приложения.
- Для чисел, дат и валют использовать helper из `packages/i18n`, а не ручную конкатенацию.
- Если текст содержит HTML/React nodes, использовать безопасный rich-text API i18n-библиотеки.
- Не складывать фразы из кусочков, если порядок слов зависит от языка.

Плохо:

```ts
`${count} товаров`
```

Хорошо:

```ts
t("marketplace.product.count", { count })
```

## Правила для API ошибок

Backend не должен возвращать финальный пользовательский текст как единственный источник ошибки. API возвращает:

```json
{
  "error": {
    "code": "payment_required",
    "message": "Payment is required",
    "i18n_key": "errors.payment.required",
    "details": {
      "field": "payment_method"
    },
    "request_id": "req_123"
  }
}
```

Правила:

- `code` стабилен и на английском.
- `message` технический fallback на английском.
- `i18n_key` используется frontend для локализованного текста.
- `details` не должен содержать секреты.

## Правила для писем

Письма должны иметь шаблоны:

```txt
packages/i18n/locales/ru/emails.json
packages/i18n/locales/en/emails.json
```

Шаблоны должны поддерживать:

- subject;
- preview text;
- body text;
- CTA label;
- legal footer;
- unsubscribe text, если применимо.

Юридические и маркетинговые формулировки требуют проверки перед production.

## Правила для уведомлений

Уведомления должны хранить:

- `type`;
- `i18n_key`;
- `payload`;
- `locale` на момент отправки, если уведомление материализуется;
- `created_at`;
- `read_at`.

Realtime-события не должны зависеть от русского текста. WebSocket отправляет event type и payload.

## Форматы дат, чисел и валют

Требования:

- Деньги хранить в minor units: `amount_minor`.
- Валюту хранить отдельно: `currency`.
- Для отображения использовать `Intl.NumberFormat`.
- Даты хранить в UTC.
- Для отображения использовать локаль и timezone пользователя.
- Не писать вручную `руб.`, `₽`, `$`.

Примеры:

```ts
formatMoney({ amountMinor: 19900, currency: "RUB", locale: "ru" })
formatDate(order.createdAt, { locale: "ru", timeZone: user.timeZone })
```

## Локализация юридических текстов

Юридические документы не должны быть зашиты в компоненты. В MVP можно использовать placeholders:

- `terms_of_service`;
- `seller_offer`;
- `privacy_policy`;
- `refund_policy`;
- `category_rules`.

Каждый placeholder должен быть помечен как `LEGAL_REVIEW_REQUIRED`, пока юрист не подтвердил текст.

## Checklist для агента

- Добавил ли новый текст в `ru` и `en`?
- Нет ли строк UI прямо в JSX?
- Есть ли `i18n_key` у новых ошибок API?
- Форматируются ли деньги через helper?
- Форматируются ли даты через helper?
- Не зашит ли юридический текст в компонент?
