# DECISIONS.md

## ADR-048: наблюдать за мостом VM без автоматического переподключения

Статус: принято, FF-0010, 24.09.2026.

После сброса физического Ethernet обе VM оставались доступными Windows-хосту, но потеряли связь с роутером. Одной проверки HTTP на самом хосте недостаточно, чтобы распознать этот отказ. Локальное задание раз в две минуты проверяет SSH обеих VM и достижимость роутера из каждой; две последовательные неудачи создают статус `alert`. Отдельная автоматизация Codex уведомляет только при изменении состояния или устаревании файла проверки.

Переподключение фильтра VirtualBox временно прерывает сеть хоста и всех VM, поэтому монитор не выполняет его автоматически. Конфигурация с адресами и путями к SSH-ключам остаётся вне репозитория; содержимое ключей не копируется. Если хост выключен или недоступна среда Codex, уведомление может задержаться. Монитор показывает симптом и место потери связи, но не устраняет первопричину сброса Intel I211 или фильтра VirtualBox.

Уточнение ADR-046 от 24.09.2026: детектор должен различать одиночный удар и зажим между опорами. `stepSoftBody` собирает разрешённые solver-ом контакты по нормалям; встречная пара разных поверхностей означает зажим. Сжатие оценивается по фактической деформации и геометрическому зазору, потому что пружины могут удержать форму и маскировать давление. Сжатие от 18 % считается сильным; сильная скорость контакта также сохраняет такую классификацию. Возвращаемое поле `SoftBodyImpact.squeeze` содержит поверхности, ось и величину оценки; событие выдаётся при входе в зажим, а не на каждом шаге. Это эвристика для интерактивного прототипа. До production требуется прогнать сценарии с полом, краем и двумя движущимися карточками, оценить пропуски/ложные срабатывания и стоимость на слабом устройстве.

Уточнение ADR-046 от 24.09.2026: чтобы длинная грань не вытягивалась одним сегментом, движок поддерживает адаптивное подразделение физической сетки по максимальной длине локального участка. Растяжение ограничивается для каждой связи относительно её длины покоя, а суммарный ход тела остаётся свободным. Старый API с явными размерами сетки сохранён; стенд использует сетку с максимальным шагом 28 CSS px и отношением локального растяжения 1,45. Верхняя детализация ограничена девятью узлами на ось, чтобы стоимость не росла квадратично без предела.

## ADR-047: статический playground на существующем nginx

Дата: 2026-09-24. Статус: принято для `UX-TASK-044`.

Уточнение от 24.09.2026: для просмотра экспериментальной статической страницы с телефона в домашнем Wi-Fi при сбое входящего Static NAT добавлен отдельный LAN-only HTTP-порт edge. Он привязан к частному адресу edge и ограничен домашней подсетью; на роутере этот порт не публикуется. Edge проверяет TLS-сертификат FanFuel VM при проксировании. Прямое подключение iPhone к VM не прошло, хотя Windows видел этот адрес; поэтому временный Node-мост на Windows принимает запросы с домашней подсети и передаёт их edge. Мост слушает только LAN IP и разрешает GET/HEAD. Площадка не имеет входа, покупок и API, поэтому локальный HTTP допустим только для неё; публичная HTTPS-публикация и её сертификаты остаются основным путём. Это временный обход внешнего маршрута, а не замена ремонта у провайдера. Мост зависит от работающего Windows-хоста и запускается снова после его перезагрузки.

Контекст: нужен публичный тест главной с интерактивным Ойли на `playground.fanfuel.ru`, без отдельного серверного приложения и без публикации текущих незавершённых изменений основного Next.js сайта. На edge уже используются Host/SNI маршруты, TLS завершается на FanFuel VM.

Решение: Vite собирает только playground в статические файлы. Edge дополняется двумя Host/SNI маршрутами на существующую FanFuel VM; её nginx отдаёт отдельный vhost из версионированного каталога. HTTP используется только для ACME и redirect, TLS имеет отдельный сертификат certbot. Публикация переключает symlink после копирования полной сборки. На этой странице нет API, cookie, аккаунтов и платежей; фиктивные действия отключены. Nginx отдаёт noindex и CSP с локальными ресурсами. Исходный код использует общий карандашный пакет и словари i18n.

Последствия: основной `fanfuel.ru` не пересобирается и не меняет публичное API; новый release можно откатить переключением symlink. Поддерживаются ещё один сертификат и две записи маршрутизации edge. Рендер расходует ресурсы браузера пользователя, поэтому дальнейшая интеграция с реальными карточками требует измерений на мобильных устройствах и отдельного product review.

## ADR-046: мягкая решётка для интерактивного Ойли

Дата: 2026-09-23. Статус: эксперимент для `UX-TASK-043` / `UX-TASK-038`; production-интеграция не утверждена.

Контекст: пользователь хочет свободно перетаскивать Ойли на выбранную карточку и получать растяжение от скорости движения и смятие при слабом ударе. Фиксированные сценарии у одной карточки и CSS-деформация готовой картинки этому требованию не соответствуют.

Решение: для мягкого корпуса использовать малую решётку с фиксированным шагом симуляции; исходные оси карандашных штрихов и замкнутый физический силуэт привязать к её ячейкам, оставив нажим и кисть независимыми. Ограничение площади ячеек не даёт решётке выворачиваться при рывке. Жёсткость связей и восстановление формы управляются параметром мягкости. Самовыпрямление включается после контакта с опорой; в воздухе текущий наклон сохраняется. DOM-карточки регистрируются как прямоугольные контактные поверхности с устойчивыми ID, а пол — как верхняя грань. Скорость и нормаль контакта выбирают между процедурной деформацией и подготовленной сильной реакцией сверху; перетаскивание имеет pointer capture только на форме персонажа. Физика идёт шагом 1/120 с, художественное зерно обновляется дважды в секунду в покое и переносится вместе со штрихом; при движении небольшой сдвиг оси меняется на каждом показанном кадре, не чаще 24 раз/с. Первый изолированный образец реализован в `packages/pencil-engine/src/soft-body.ts` и `demo/contour.html`.

Последствия: каждое изменение формы и дискретное изменение зерна пока требуют повторного построения карандашного слоя, поэтому Worker и последний ожидающий кадр защищают ввод, но не гарантируют 24 fps на слабом устройстве. Перед включением на сайте нужны замеры, разделение мягких/жёстких частей, интеграция с клипами, доступность клавиатуры/reduced motion и проверка кликабельности произвольных карточек. Заливка остаётся вне текущего этапа.

Уточнение 24.09.2026: владелец попросил заметную перерисовку в покое и небольшое отклонение штриха на каждом новом кадре движения. Рендерер получает отдельный `redrawFrame` и ограниченный `redrawStrengthCss`; исходная геометрия, коллайдер и авторский нажим остаются прежними. Режим написания использует нулевую силу отклонения и фиксированный кадр зерна.

Коррекция 24.09.2026: частота в покое — именно два раза в секунду. Чтобы обновление было видно, по `boilFrame` меняется контакт мелкого и среднего зерна; широкий рисунок и авторский нажим сохраняются. Сила зернистого обновления остаётся связанной с ползунком художественной «живости» в стенде.

Художественная проба 24.09.2026: контакт средних и широких участков направлен вдоль штриха, расход графита за отпечаток нормирован по шагу выборки, нажим слегка меняет порог контакта. После деформации ось можно смягчить не более чем на 1,5 экранного CSS px; стенд использует 1 px. Это добавляет вычисления в покадровый путь, поэтому до production обязательны кэш материала, проверка на слабом устройстве и сравнение с авторским образцом. Физическая достоверность модели пока не подтверждена.

Коррекция после отзыва владельца 24.09.2026: прежняя нормировка частично компенсировала нажим, делая весь след серым. Расход теперь соотнесён с базовой длиной отпечатка, а его площадь и тон оба следуют нажиму; пресет Ойли усиливает амплитуду авторского профиля. Для углов вместо сдвига вершины строится короткая квадратичная дуга. Предел `smoothingCss` повышен до 2 CSS px, стенд использует 1,6. Производительность и художественный вид остаются предметом проверки перед production.

Следующая коррекция 24.09.2026: тонким деталям лица нужен отдельный нижний предел читаемости; для них повышены плотность и контакт, уменьшен размах нажима, а улыбке сокращено сужение. Сглаживание отдельных изломов заменено локальным усреднением равномерных точек вдоль всей деформированной оси. Предел `smoothingCss` — 3 CSS px; стенд стартует с 2,1 и даёт сравнить 0–3. Стоимость малого кадра в локальном стенде осталась около 3,6–4 мс на текущем ПК; слабые устройства всё ещё не измерены.

Художественное уточнение 24.09.2026: для краткого отрыва и повторного прохода использовать разные распределения возможностей. Отрыв тяготеет к поворотам, концам и смене нажима; повтор — к середине длинной прямой. Наличие и положение выбираются заново по seed показанного рисунка, затем держатся в материальных координатах до следующей перерисовки. `handwork` ограничен подвижным режимом `grainSpace: "stroke"`; письмо с открытием следа использует фиксированный кадр или отключает эффект. Это добавляет один проход по выборкам оси и требует проверки стоимости на слабом устройстве, но не меняет физический контур или заливку.

Коррекция по повторному просмотру 24.09.2026: проба с узким настоящим просветом в стыке отвергнута владельцем. Текущий стык сохраняет непрерывный основной след и добавляет короткий, чуть смещённый второй жест с асимметричными концами. Это даёт локальное наложение вместо белой дырки; положение меняется по кадрам, а вероятность зависит от поворотов, концов и перемены нажима. На наиболее резких углах рисовать отдельное короткое продолжение одной или обеих касательных за вершину, не меняя физическую ось. Замкнутый шов включать в анализ кривизны. Насыщенность и частота повторного прохода достигают прежнего максимума при 50 % `handwork`; остальная шкала сохраняет регулировку стыков. Пиксельная маска просвета удалена, но до production нужны замеры и кэш частей.

Дополнение 24.09.2026 для округлых петель: после деформации оценивать компактность `4πA/P²`; при значении выше `0,86` выбирать один стык с предпочтением нижней дуги в экранных координатах. Это отвечает наблюдению владельца о слишком правильных глазах, но не изменяет геометрию или коллайдер. Длина второго жеста ограничена долей периметра, на округлой петле отключён дополнительный случайный повтор. Метрика вычисляется один раз на петлю и передаётся выбору кандидатов; это линейный проход по выборкам без пиксельной маски. Порог и сила стыка требуют художественной проверки после сильной деформации и на повёрнутых объектах.

Коррекция после просмотра: прежнее смещение лежало внутри ядра штриха и почти не читалось. Для округлой петли короткий второй след вынесен дальше от оси, ограничен 4,5 % периметра и чаще выбирается строго на нижней дуге; основная линия остаётся непрерывной. Эффект допускается и с неподвижным бумажным зерном, чтобы большой сравнительный контур отражал тот же приём. Это повышает цену только отмеченных линий; для письма без покадровой смены сохранять фиксированный рисунок или `handwork: 0`. Публичный runtime и физический коллайдер не меняются.

Уточнение после нового отзыва 24.09.2026: предыдущий добавочный след на округлой петле отвергнут. В короткой зоне рендерить два конца исходного штриха с небольшим продольным наложением и поперечным пересечением; непрерывный исходный след в этой зоне не наносить. При сравнении с фотографией владельца первая версия этого разбиения дала грубый излом и тёмный узел. Поэтому точку выбирают ближе к нижнему экстремуму глаза, боковое отклонение затухает к краям, а сумма плотностей двух концов остаётся близкой к плотности одного следа. Решение касается только карандашного материала округлой петли и не меняет физическую геометрию. Механизм стыков остальных форм пока остаётся прежним; художественная мера и стоимость требуют проверки.

Дальнейшая художественная проба: в центре большого округлого контура добавлен неглубокий локальный угол с плавным входом в исходную дугу. На короткой петле он затухает; после проверки четырёх последовательных кадров амплитуда уменьшена, чтобы не усиливать существующий поворот до крючка. Место выбирается среди нижних 2,5 % высоты петли. Результат остаётся процедурной аппроксимацией; без авторской разметки стыка нельзя гарантировать одинаково удачную форму на каждом исходном пути.

Следующая коррекция после фотографии с серией овалов: локальный угол отменён, так как владелец видит в нём выпуклый «прыщик». На округлой петле сохранять внешний силуэт исходной дуги, а различие двух жестов выражать коротким внутренним отклонением второго конца и умеренным накоплением графита в их продольном перекрытии. Направление внутрь вычислять по знаку площади пути, чтобы результат не зависел от обхода. В 96 % кадров искать соединение в нижних 5 % высоты, в остальных допускать другую точку; амплитуду менять по seed, включая почти идеальное соединение. Путь и коллайдер не менять. Художественная оценка владельца всё ещё требуется; для целевого ассета позднее предусмотреть авторскую разметку места стыка.

Коррекция после просмотра анимированного глаза: широкая процедурная деформация всей округлой оси дала волнистую форму и визуально частую пульсацию, поэтому она отменена. Для округлой петли допустимо только малое, постоянное по штриху смещение (не более `0,18 × widthCss × handwork` до коэффициента длины); покадровая составляющая оси ограничена 35 % общей настройки. Профиль плавного нажима сохраняется по `id`/seed, а новые рисунки меняют зерно и короткий стык. Цена дополнительного расчёта остаётся линейной по отсчётам контура и не требует ещё одной пиксельной маски; время на слабом устройстве всё ещё не измерено. Нерегулярную форму самого глаза нужно задавать авторским путём, не шумом рендера. Художественный статус остаётся экспериментальным.

Повторная коррекция по просьбе владельца: предел `0,18` сделал глаза слишком правильными. Основной медленный изгиб теперь достигает `1,1 × widthCss × handwork` с коэффициентом длины, но фиксируется по `id`/seed; только меньшая добавка `0,2 × widthCss × handwork` обновляется по `boilFrame` (обычно 2 раза/с). Быстрое `redrawFrame` всё ещё получает 35 % общей настройки для округлой петли. Это сохраняет характерную неправильность без быстрой пульсации формы. Стык строится из перекрывающихся концов: один идёт по основной дуге, другой короче, тоньше и светлее, они обмениваются положением внутри края. Производительность и художественное принятие остаются открытыми.

Последняя коррекция по уточнению владельца: удержание формы и стыка до `boilFrame` отменено. Округлый глаз должен получать новый рисунок на каждом `redrawFrame`; уменьшается **только амплитуда** поперечной вариации до `0,9 × widthCss × handwork` с коэффициентом длины. Сохраняются два плавных пространственных изгиба и ослабленный общий `redrawStrengthCss` (35 %), без третьей короткой волны. Профиль авторского нажима остаётся постоянным. Такое разделение разрешает покадровую жизнь линии при ограниченном уходе глаза от исходной формы. Художественное принятие и цена пересборки остаются открытыми.

Коррекция стыка по серии кадров: случайный знак отклонения иногда уводил единственный плотный конец внутрь и создавал видимость дырки. Тонкий второй проход иногда становился единственным продолжением и выглядел как провал толщины; при полном наложении возникал тёмный узел. Теперь на каждой стороне встречи есть один конец с полной шириной, тоном и исходной осью; только перекрывающий вспомогательный хвост отклоняется внутрь и истончается. Депозит двух проходов ослабляется в общей зоне. Новых буферов или проходов по пикселям нет, изменение локально для уже выбранного стыка. Порядок передачи проверяется адресным тестом, визуальная оценка остаётся открытой.

Коррекция 24.09.2026 по последовательным контактам: demo объединяет близкие во времени физические события в один эпизод реакции на 750 мс, который продлевается каждым новым касанием. Выбранный тип можно только повысить в порядке «мягкий край → мягкая опора → сильный край → сильная опора»; слабый отскок не перезапускает и не переименовывает уже выбранную сильную реакцию. Захват начинает новый эпизод. Порог и расчёт скорости `stepSoftBody` не меняются; фильтр остаётся на уровне демо и не добавляет работы в фиксированный шаг физики.

## ADR-045: DOM-сцена Ойли поверх существующего сайта

Дата: 2026-09-23. Статус: проектное направление для `UX-TASK-043` и UI-пилота `UX-TASK-038`.

Контекст: владелец хочет, чтобы Ойли визуально взаимодействовал с сайтом: появлялся у хедера, падал на нижнюю видимую поверхность и реагировал на карточку товара. Существующий `OilyStage` перемещает один SVG-actor между DOM-якорями, но не имеет сценариев и контактных поверхностей. Отдельная World-страница остаётся `FUTURE` и не нужна для этого эффекта.

Решение: добавить в actor runtime прозрачный `SiteStage` поверх выбранных существующих страниц, реестр смысловых DOM-якорей/контактных поверхностей и `SceneDirector` для коротких сценариев. Координаты элементов брать из актуальной раскладки; прокрутка, resize, загрузка карточек и route change обновляют привязки. Визуальные контакты запускают клипы Ойли и обратную связь элемента без изменения торговых данных. Рендер карандашного персонажа кэширует материалы отдельно от каждого кадрового движения. Ввод проходит сквозь слой, кроме явно интерактивной области персонажа. Первая сцена ограничивается хедером и нижней поверхностью первого viewport, а не невидимым концом длинного документа.

Последствия: нужно проверять корректность координат при sticky header, прокрутке, layout shift и смене маршрута, ограничить частоту сцен, обеспечить reduced-motion/static fallback и не перекрывать карточки/CTA/диалоги. UI-пилот проводится на `/` и `/marketplace`; checkout и чувствительные финансовые состояния исключены. Full World/economy остаются вне scope. Детальный план: `docs/PENCIL_ENGINE_WEB_STAGE.md`.

## ADR-044: actor runtime поверх исходных карандашных штрихов

Дата: 2026-09-23. Статус: проектное направление для `UX-TASK-043`, техническая проверка впереди.

Контекст: владельцу понравился след из поля рисования пером. Для разных действий и размеров экрана нельзя готовить отдельную полную анимацию; полная растеризация контуров на каждом кадре также слишком дорога. В пакете уже есть прототип групп и спрайтов, но он использует прежний отвергнутый алгоритм штриха и не работает с записанными отсчётами пера.

Решение: хранить исходные штрихи с нажимом и наклоном в локальных частях персонажа; строить иерархию точек вращения, небольшие наборы сменных векторных рисунков и клипы ключевых поз. Контроллер выбирает и смешивает действия. Экранный размер влияет на камеру и размерный уровень растеризации, но не на исходные клипы; ширина грифеля остаётся независимой `widthCss`. Подготовленные слои кэшируются по версии ассета/кисти, размерному уровню, DPR, seed и варианту формы. Перенос/поворот готовых жёстких частей выполняется композицией; изменённая форма перестраивается локально. `held`/`drawOn` сохраняют фактуру, `boil` меняет только ограниченную микрофактуру. Точный формат и размеры кэша выбираются после вертикального прототипа и измерений.

Последствия: нужно объединить новый контурный рендер и модель движения, а также добавить авторинг частей и pivot; наличие старого `sprite` не решает эту интеграцию. Некоторые позы и сменные формы всё равно создаются художником, но не для каждого шага или размера. Кэш тратит память и имеет холодную стоимость подготовки; бюджет CPU/памяти проверяется на слабом устройстве и в OBS. Детальный план и критерии: `docs/PENCIL_ENGINE_RUNTIME.md`.

## ADR-043: частичный импорт кистей и запись исходных данных пера

Дата: 2026-09-23. Статус: эксперимент для `UX-TASK-043`.

Контекст: скачанные владельцем Photoshop ABR и GIMP VBR/GDYN имеют разные модели наконечника и динамики. Обещание полного совпадения без соответствующего движка кистей вводило бы в заблуждение. Большие растровые маски и архивы могут создавать нагрузку при импорте; покадровая генерация контура ещё не укладывается в согласованный бюджет анимации.

Решение: извлекать только sampled tip из ABR v6, параметрический tip из VBR и tip из GBR v2; `.gdyn` и динамику ABR не выполнять. ZIP читать без распаковки на диск, с лимитами размера, числа файлов/наконечников и исходных пикселей. Большие маски ABR усреднять до 128 px; импорт происходит при выборе файла, а не в каждом анимационном кадре. Конфигурацию нажима и сужения держать отдельно от геометрии пути. Записывать исходные `PointerEvent` samples в версионированный JSON: давление, наклон, поворот и выбранную базовую ширину штриха; отрисовку можно совершенствовать без потери записанных отсчётов. Не загружать архивы или JSON на сервер.

Последствия: точная совместимость Photoshop/GIMP отсутствует, а разрешение маски намеренно снижено под текущую ширину грифеля. Сборка статичного слоя остаётся затратной и должна переиспользоваться для анимации. Наклон пока хранится, но не влияет на рендер; до production нужен тест реального планшета и лимиты для полного формата сцен.

## Дополнение к ADR-кандидату UX-TASK-043: ширина карандашного контура

Дата: 2026-09-23. Статус: эксперимент, художественное решение не принято. По уточнению владельца первый этап ограничен контуром; работа над заливкой отложена. Ширина грифеля задаётся отдельно от масштаба изображения в CSS px, чтобы крупный и мелкий Ойли выглядели как два рисунка одной кистью. Статичный `renderPencilContours()` заново рассчитывает контакт с бумагой при размере вывода. Это повышает стоимость холодной сборки и потребление памяти на больших холстах; до выбора анимационного backend требуются художественная оценка и замеры на слабом устройстве. См. `docs/PENCIL_ENGINE_VISUAL_REWORK.md` и `packages/pencil-engine/demo/contour.html`.

Дополнение после замеров: рабочие буферы ограничены охватывающим прямоугольником путей и сведены к прозрачности, бумажному контакту, идентификатору цвета и RGBA. Статичная генерация в демо идёт через Web Worker/OffscreenCanvas при поддержке браузера, с синхронным запасным путём. Отрисованный слой должен переиспользоваться между кадрами; worker переносит вычисление, но не делает его бесплатным. Выбор окончательного Canvas/WebGL backend и бюджет 24 fps остаются открытыми до теста на физическом слабом устройстве и после художественного принятия контура.

Уточнение 24.09.2026: покадровая плавная вариация оси применяется ко всем замкнутым контурам, чтобы глаза и силуэт двигались сопоставимо. Это несколько дополнительных вычислений на уже выбранный образец линии, без второго полного слоя и без изменения физического пути. Для округлого стыка рендер двух концов ограничен короткой локальной зоной; сумма их весов ограничена, внутренний конец использует одно волокно. Художественная мера остаётся экспериментальной. После этой правки нужны отдельные замеры холодной сборки и кадрового бюджета перед переносом в production: локальные тесты не доказывают производительность на слабом устройстве.

Наконечник `.gbr` v2 подключён к контурному рендеру как сменная альфа-маска. Это ограниченная совместимость формата ресурса; динамика GIMP, MyPaint, Photoshop и Procreate не переносится автоматически. Сторонний ассет не включён без проверки конкретного карандашного образца и лицензии.

Художественное уточнение: несколько осмысленных открытых проходов с локальным перекрытием задаются отдельными путями сцены, а `fray` управляет только слабым следом графитных волокон по их краям. Это сохраняет физическую ширину кисти отдельно от размера персонажа и позволяет канистре иметь более чистый край, чем тело. Прогретая сборка 1000 CSS px/DPR 2 после изменения осталась около 36 мс на контрольном ПК; нового обязательства на покадровую полную регенерацию нет. Статус художественного метода остаётся экспериментальным.

Последующая оценка владельца выявила избыточный контраст и рябь от дополнительных волокон и случайного нажима. Для текущего образца выбран один контактный отпечаток с постоянным основным профилем ширины; бумажный контакт влияет на прозрачность и кромку. `fray` остаётся необязательным параметром API, но выключен в образце. Это уменьшает число отпечатков и избегает заметного двоения. Геометрию больше не пересматривать без нового запроса; статичная сборка по-прежнему отделена от кадровой анимации.

Коррекция после следующего художественного отзыва: одно контактное ядро оказалось похожим на маркер. Для текущего образца возвращены три близких волокна и частичный контакт с бумагой; `fray: 0`, случайное давление и смещение оси не возвращены. Прогретый расчёт 1000 CSS px/DPR 2 на контрольном ПК — порядка 35 мс. Геометрия, разделение статичной сборки и кадровой анимации остаются прежними.

Следующее уточнение: вариация нажима необходима, но должна быть управляемой и плавной. Принято хранить необязательный `pressureProfile` на отдельном штрихе как опорные значения по нормализованной длине; пропущенный профиль получает медленный детерминированный жест. Это не меняет геометрию и базовую ширину кисти в CSS px. Полный профиль остаётся частью подготовленных данных сцены, поэтому в кадровой анимации его следует переиспользовать, а не генерировать заново каждый кадр.

Последующий просмотр потребовал большей амплитуды и заострения концов. Диапазон профиля теперь 0,55–1,4; открытый штрих получает короткий плавный концевой taper, а у стыков составного силуэта taper можно отключить. Время и направление жеста по-прежнему привязаны к длине пути, поэтому изменение масштаба не меняет последовательность усилений. Геометрия пути остаётся независимой от ширины грифеля.

## ADR-кандидат: 2026-09-23 — рендер из направленных карандашных штрихов (UX-TASK-043)

Статус: `proposed`, ожидает проверки статичного художественного эталона. После отказа владельца от вида `0.1.0` предлагаем разделить данные рисунка на маски/контуры, направляющие штрихов, тон, слои и профили кисти; малые текстуры наконечника и бумаги использовать как материал, а не как готовое изображение персонажа. Генерацию больших штрихов закреплять в координатах объекта; уровни детализации добавлять при масштабе без полной смены seed. Рендерер сначала должен совпасть с утверждённым статичным фрагментом, затем решается runtime backend и бюджет анимации. Ранний выбор WebGL2 или Canvas 2D как окончательного backend пока не принят. Масштабируемость и риски описаны в `docs/PENCIL_ENGINE_VISUAL_REWORK.md`. Это предложение не меняет принятое решение держать эксперимент вне production web.

Уточнение по запросу владельца: траектория и сменный пресет кисти хранятся отдельно. Первым открытым форматом наконечника выбран `.gbr` v2, кандидатом для динамического пресета — `.myb`/libmypaint после проверки визуальной точности и WASM-бюджета. Внутренний контракт не зависит от Photoshop, Illustrator, Procreate или Toon Boom; их пресеты не объявляются точно переносимыми. Акварель требует отдельного материала, а не только другого наконечника. Решение и источники: `docs/PENCIL_ENGINE_BRUSHES.md`. Статус остаётся `proposed` до проверки образца и производительности.

Первый сравнительный образец `demo/study.html` реализует смену трёх пресетов и импорт `.gbr` v2 в отдельном статичном рендере. Просмотр показал недостаточное художественное сходство, поэтому архитектура полного формата сцены и выбор быстрого backend по-прежнему не приняты. Измерения настольного Chrome относятся только к этому образцу, не к целевой анимации.

После обратной связи по «вырезанному» краю и размытой обводке у тела выделен сухой контур, а канистра оставлена с прежним. Для проверки бюджета статичный слой кэшируется по размеру/кистям, поверх него обновляется только малая микрофактура при 24 кадрах/с. Кэш ограничен двумя конфигурациями; холодная сборка на слабом CPU остаётся дорогой и может блокировать интерфейс. Это экспериментальная схема, не решение о production Canvas backend.

## ADR: 2026-09-23 — изолированный Canvas-прототип карандашной анимации (UX-TASK-043)

Контекст: текущий WebP Ойли сохраняет фактуру, но не даёт перерисовывать штрихи на разных масштабах и анимировать векторные части. Пользователь запросил собственный движок по предоставленному рисунку. Решение: технический прототип в отдельном пакете с векторными путями, seed-зависимой фактурой и Canvas 2D. В режиме `boil` штрихи меняются дискретно; при `reveal` seed фиксируется. Скелет задаётся вложенными группами, спрайт — векторными кадрами. Ограничены DPR, плотность штрихов и кэши; цикл останавливается вне экрана, в скрытой вкладке и при reduced motion/Save-Data. Это не отменяет прежний ADR о лёгком production web experience: подключение к web требует отдельного художественного и performance review. Рассмотрены PNG/WebP (не масштабируются и не дают генеративных кадров), чистый SVG/CSS (сложная плотная фактура дорога или статична), WebGL (ранняя сложность без замеров). Риски: неполное сходство с референсом, ручной авторинг глифов, отсутствие измерений на слабых устройствах и ограниченного безопасного импортера. Подробности: `docs/PENCIL_ENGINE.md`.

## ADR-0018: Studio statistics и bot events как provider-agnostic activity layer

## ADR-0020: Отдельная VM приложения и отдельный edge nginx

Дата: 2026-09-14. Статус: принято для задачи FF-0009.

### Контекст

Пользователь запросил новую VM FanFuel на диске D: и затем уточнил, что nginx будет размещён на другой VM. Существующие VM других проектов не используются для приложения.

### Решение

- Отдельная Ubuntu 24.04 VM, Docker Compose и постоянные volumes приложения.
- `docker-compose.vm.yml` применяется после base/dev файлов; Next.js запускается через `next start`, Vite-приложения собираются в статические файлы.
- `APP_ENV=production` отключает dev bootstrap администратора и включает точный CORS allowlist. Это технический режим запуска, а не признание готовности платежей к production.
- Секреты генерируются отдельно на VM, `.env` имеет права 0600; SSH использует отдельный ключ вне Git.
- Базы, storage API/console, worker и admin привязаны к loopback. Web/API/WS/widget публикуются на LAN-адресе VM для будущего edge.
- `DOCKER-USER` ограничивает вход из LAN к прикладным контейнерам. До получения адреса nginx VM разрешена локальная подсеть; затем правило следует сузить до адреса edge и необходимых административных источников. UFW сам по себе не защищает published Docker ports.
- nginx/TLS/внешние пробросы остаются отдельным шагом по просьбе пользователя. Созданный до уточнения HTTP bootstrap внутри FanFuel VM далее не изменяется и не считается финальным edge.

### Последствия

- В публичной конфигурации edge потребуются TLS, проксирование HTTP/WebSocket, ограничения auth/API и запрет публикации mock callbacks/admin API.
- Реальные платежи, выплаты и legal readiness остаются за пределами задачи. `LEGAL_REVIEW_REQUIRED` и provider review сохраняются.
- Нужно закрепить LAN-адрес VM через DHCP reservation; фактические адреса и SSH-доступы записаны только в игнорируемом `docs/SERVER_ACCESS.md`.
- Перезапуск контейнеров обеспечен `unless-stopped`, firewall восстанавливается systemd. Автозапуск самой VM при старте Windows отдельно не настраивается.

Дополнение FF-0009: недоступный Docker Hub образ MinIO заменён только в VM override на официальный Quay image с закреплённым digest. Storage не публикуется в LAN; обновление/поддержка object storage требует отдельного решения перед публичным использованием файлов.

## ADR-0021: Публичный Host/SNI edge и TLS на VM приложения

Дата: 2026-09-14. Статус: принято. TASK-ID: FF-0010. Уточняет ADR-0020.

- Общий edge сохраняет TLS passthrough для LibreChat; добавлены только домены FanFuel в Host/SNI maps.
- TCP 80/443 роутера направлены на edge; новые SSH-пробросы не создаются. Остальные правила роутера не меняются.
- HTTPS завершается на FanFuel VM, где установлен certbot и достаточно места для него. На маленьком системном диске Alpine edge certbot не используется.

- Let's Encrypt сертификат покрывает основной и www-домен. Обновление выполняет certbot.timer с nginx reload hook.
- Public admin API и mock callbacks запрещены на nginx; реальные платежи и legal readiness этим не включаются.
- Ограничение принятой схемы: исходный TLS client IP до приложения не передаётся, лимиты nginx агрегируются по IP edge. Улучшение требует PROXY protocol или изменения места TLS termination; в текущей задаче работающий LibreChat transport не меняется.

## ADR-0022: Базовая регистрация без role intent и имени платформы

Дата: 2026-09-14. Статус: принято. TASK-ID: UX-TASK-032.

### Контекст

Регистрация просила имя на платформе и роль для старта. Это смешивало три разных значения: имя для интерфейса, публичный ник/название витрины и будущий username, а также заставляло выбирать роль до первого опыта в продукте. Backend по role intent сразу создавал creator/seller profile.

### Решение

- `POST /api/v1/auth/register` принимает только `email`, `password` и optional locale/time zone.
- Публичная регистрация всегда создаёт базовый аккаунт с ролью `buyer`.
- `display_name` и `role_intent` удалены из request contract; старые клиенты должны обновиться.
- Профиль создаётся с временным display name и `name_confirmed_at = null`.
- Следующий обязательный шаг — `/auth/name`; он сохраняет имя через `PATCH /api/v1/me/profile`.
- Текущему пользователю API возвращает `profile_name_confirmed_at`; публичные profile responses не раскрывают этот маркер.
- Режимы автора/продавца включаются отдельными явными сценариями после базового аккаунта.
- Существующие профили в миграции помечаются подтверждёнными, чтобы не заставлять текущих пользователей повторять шаг.

### Последствия

- Это локальное pre-beta breaking change публичного auth contract; оно зафиксировано здесь и в `docs/API_PLAN.md`.
- После подключения email verification шаг имени должен идти после реального подтверждения email, но смысл поля не меняется.
- Имя платформы, публичный ник/название витрины и username остаются отдельными значениями и не резервируют друг друга.

## ADR — UX-TASK-031: создание авторского черновика после входа

Решение: публичная анкета хранит только название/описание в sessionStorage; серверное создание выполняется после авторизации и явного сохранения. Фиксированный auth-return исключает внешний redirect. POST onboarding выдаёт только роль streamer своему пользователю (как существующая регистрация), блокирует повторное создание блокировкой строки пользователя, не изменяет существующие страницы и пишет audit log. Публикация отдельная.

UX-TASK-031: обнаружена выдача draft авторов публичными GET и допустимость draft в разрешении адресата доната. В связи с созданием приватных черновиков разрешён только published; PublicProfile скрывает непубличный creator_profile. Provider/суммы/проведение платежей не меняются. Изменение доступа намеренное, чтобы черновик не был публичным до публикации.

## ADR-0023: UX авторизации без публичного определения наличия аккаунта

Дата: 2026-09-15. Статус: принято. TASK-ID: UX-TASK-033.

Сохраняем email/password и фиксированные переходы marketplace/name/creator. Не вводим endpoint проверки существования пользователя, вход по display_name/slug или телефону. Будущая автоматическая развилка требует подтверждения владения email и отдельного backend/security проекта; обоснование и источники — `docs/AUTH_UX_REVIEW.md`.

Пароль не сохраняется при смене режима, email живёт только в памяти auth layout. Текущая политика JWT/localStorage не меняется. Ошибка сети при проверке сессии не является доказательством невалидного токена; очищать его можно при unauthorized либо явном выборе другого аккаунта. Проверка регистрации на клиенте учитывает фактический предел bcrypt в 72 UTF-8 байта без обрезания пароля; серверная политика требует отдельного выравнивания, см. DESIGN_AUDIT.

## ADR-0024: Подтверждение email до регистрации и единый identifier-first flow

Дата: 2026-09-17. Статус: принято. TASK-ID: UX-TASK-035. Заменяет решение ADR-0023 о запрете публичной развилки.

### Контекст

Пользователь явно запросил обязательное подтверждение почты и объединение отдельных страниц входа/регистрации. Текущий backend создаёт активный аккаунт сразу по email/password и не отправляет письма. Телефон и account username пока отсутствуют в домене.

### Решение

- Канонический маршрут авторизации — `/auth`; старые `/auth/login` и `/auth/register` выполняют совместимый redirect.
- `POST /auth/identify` определяет только существование email и возвращает `login` либо `register`.
- Новый аккаунт не создаётся до подтверждения одноразового кода.
- Код живёт 10 минут, имеет максимум 5 попыток, resend cooldown 60 секунд, хранится только как HMAC digest и инвалидирует предыдущий challenge.
- После проверки кода выдаётся короткоживущий registration JWT, привязанный к email и challenge. Challenge помечается завершённым в транзакции создания пользователя, поэтому token нельзя применить повторно.
- Письма отправляются через `EmailSender`; первая реализация использует SMTP из environment, а dev stack — Mailpit. Синхронная отправка из API принята как временный MVP; перенос в worker/queue нужен до существенной нагрузки.
- Аккаунты, существующие до миграции, получают `email_verified_at` из `created_at`, чтобы rollout не блокировал текущий вход.

### Security-компромисс

Ответ `identify` раскрывает факт существования аккаунта. Это осознанно принято ради парольного входа без OTP на каждом посещении. Ограничения: rate limit по IP и identifier, одинаковый HTTP status, отсутствие профиля/статуса/ролей в ответе. Более строгий будущий вариант должен подтверждать владение email до выбора режима либо использовать единый OTP/passkey flow.

### Последствия

Контракт регистрации меняется до public beta: вместо email требуется registration token. Нужны миграция challenge-таблицы, SMTP readiness, мониторинг доставки и cleanup истёкших challenge. Телефон/username не добавляются этой задачей.

## ADR-0025: Допуск категорий цифрового доступа только после проверки передаваемости

Дата: 2026-09-21. Статус: принято как правило MVP. TASK-ID: FF-1004.

### Контекст

Первичный поиск продавцов рассматривает аккаунты, подписки, ключи и пополнения. Прежнее правило исключало все такие товары из MVP одним списком. Это слишком грубо для официальных gift codes и разрешённых способов пополнения, но снятие ограничения для любого «личного» аккаунта создаёт другой риск: законное создание или оплата аккаунта не означает, что договор исходной платформы разрешает его продать или передать.

### Решение

- Категории цифрового доступа остаются `restricted` по умолчанию, но не считаются навсегда запрещёнными одним общим правилом.
- Review проводится отдельно для каждой исходной платформы, подкатегории и способа исполнения.
- Для допуска нужны законное происхождение, доказуемое право продавца на передачу, явное разрешение исходной платформы, payment-provider approval, правила модерации, anti-fraud, privacy и refund/dispute policy.
- Украденные, взломанные, shared, promo-abuse и содержащие чужие данные аккаунты запрещены без исключений.
- FanFuel не хранит пароли, session cookies, recovery codes, API keys и raw 2FA secrets.
- Аккаунты Steam и личные аккаунты ChatGPT/OpenAI не допускаются по действующим на дату решения правилам сервисов. Google/Gemini и Perplexity остаются непроверенными и не открываются без отдельного решения.
- Официальные gift codes, лицензионные ключи, переносимые цифровые права и пополнения через разрешённые каналы могут пройти отдельный review; они не получают автоматического разрешения вместе со всей категорией.

### Последствия

- Текущий каталог и API не меняются; restricted категории не открываются этой документационной правкой.
- Работа с потенциальными продавцами не должна обещать приём конкретного аккаунта, ключа или пополнения до category-specific review.
- Перед фактическим включением подкатегории требуется новый ADR или дополнение к этому ADR с источниками, датой проверки и решением legal/payment/provider review.

## ADR-0026: Автозапуск VM и диагностика повторяющихся зависаний

Дата: 2026-09-22. Статус: принято как временная эксплуатационная мера. TASK-ID: FF-0009/FF-0010.

### Контекст

VM FanFuel повторно переставала отвечать, оставаясь в состоянии VirtualBox running. В журналах Ubuntu за 15, 17 и 18 сентября перед soft lockup видны большие задержки clocksource и RCU stall. На Windows запущен Hyper-V, а VirtualBox сообщает AMD-V is not available и переходит на NEM. Контейнерные healthchecks и задача запуска VM не обнаруживают зависание всей гостевой ОС.

### Решение

- Запускать VM при старте Windows отдельным заданием Task Scheduler с триггером AtStartup, учётной записью remot и S4U; существующий триггер при входе пользователя оставить резервным. Скрипт в C:\ProgramData\FanFuel\start-vms.ps1 проверяет состояние VM, пишет локальный журнал и возвращает ненулевой код при ошибке.
- Не выполнять автоматический принудительный reset VM с PostgreSQL по одному неуспешному HTTP-запросу.
- Считать конфликт Hyper-V/VirtualBox наиболее вероятной причиной, но не объявлять его доказанным до контрольной работы VM без Hyper-V. Отключение Hyper-V или средств защиты Windows и перезагрузку хоста выполнять только после оценки зависимых функций и согласования окна обслуживания.

### Последствия

Автозапуск при boot больше не зависит от входа пользователя. Он поднимает выключенные VM, но не лечит зависшую VM. Для устойчивой публикации нужен отдельный выбор совместимой конфигурации гипервизора или перенос сервиса на постоянно доступный Linux-хост, затем наблюдение за журналами и повторная проверка доступности.

Ограничение текущего хоста: Windows 11 Home не предоставляет полноценную роль Hyper-V для VM. Перенос VM в Hyper-V потребует обновления до Pro; до появления отдельного сервера предпочтителен контрольный запуск VirtualBox с прямой AMD-V без конкурирующего гипервизора Windows, с учётом влияния на функции безопасности Windows.

Пользователь согласовал однократную проверку с перезагрузкой ПК. Для неё создана отдельная запись BCD с `hypervisorlaunchtype off`; исходная запись остаётся загрузкой по умолчанию. Проверка должна показать, получает ли VirtualBox прямую AMD-V и прекращаются ли задержки гостевого ядра. После первой загрузки решение о постоянном режиме принимать по наблюдению, а не по одному успешному HTTP-запросу. Во время тестовой загрузки функции Windows, зависящие от гипервизора и VBS, временно недоступны.

Первый результат: контрольная загрузка дала `HypervisorPresent=False`; VirtualBox включил SVM и RealTSCOffset без NEM, задания автозапуска и проверки завершились с кодом 0, публичные web/API ответили 200. Это подтверждает устранение конкуренции гипервизоров в текущей загрузке, но не доказывает долговременную устойчивость. Решение о постоянном отключении гипервизора Windows отложено до наблюдения за журналом ядра FanFuel; недоступность SSH у InsideApiVezde требует отдельной диагностики.
Уточнение: InsideApiVezde показывает штатный экран входа Ubuntu, хотя SSH не выдаёт приветствие; причину её недоступности нельзя считать установленной.

## ADR-041: точное сравнение товаров и явная атрибуция

Дополнение: пользовательские avatar/banner загружаются по подписанному одноразовому URL; сервер удаляет metadata перекодированием и ограничивает размер/пиксели. Локальный адаптер отделён от домена интерфейсом MediaStorage и запрещён в production. Публичный доступ проверяет связь файла с опубликованной витриной; preview требует владельца. Внешние URL/CSS/HTML не исполняются.

Статус: принято, UX-TASK-041, 22.09.2026.

Контекст: названия товаров неоднозначны; высокий процент поддержки не доказывает выгодность. Согласованы финансирование из выручки продавца и выбор получателя покупателем.

Решение: отдельное произведение и строгая сигнатура варианта с версией схемы. Fuzzy-поиск помогает найти кандидатов, но не подтверждает эквивалентность. SQL-фильтры формата/региона/платформы не смягчаются автоматически. Ранжирование не использует комиссию автора. Ориентир цены — медиана независимых продавцов, свежесть, выбросы и минимальный размер выборки. Статистическая неопределённость показывается явно. Прогнозы без событий не генерируются.

Ставки и атрибуция проверяются сервером и фиксируются в заказе. Публикация legacy-товаров потребует явной настройки, существующие заказы неизменны. Creator settings имеют optimistic revision и ownership check. Поиск ограничен по длине/выдаче; индексы GIN FTS и btree variant обеспечивают рост без сканирования в приложении. Персонализация и риск-флаги не являются доказательством мошенничества.

Дизайн: локальные Golos/Caveat, оптимизированный graphite WebP 48 КБ для Ойли, SVG для знаков и интерфейса. Сложная растровая фактура только у персонажа; вместо дорогостоящего procedural noise на каждом кадре. Motion учитывает reduced motion и Save-Data.

### Дополнение ADR-041: поиск, перенос поддержки и совместимость

22.09.2026. Точная группировка выполняется внутри variant_key+currency, неизвестные значения остаются самостоятельными. Marketplace выводит минимальную цену группы; creator picker показывает каждого продавца. Название/fuzzy-match не являются ключом идентичности. Variant канонизируется и не принимает unknown как известный регион.

Локальные saved/cart хранят недоверенный ref; каждый заказ повторно проверяет его. Quote fingerprint защищает новый checkout от изменения условий. Buyer-scoped idempotency + advisory transaction lock предотвращают параллельный повтор mock provider вызова. Миграции 000008–000010 обратимы на тестовой схеме; extension pg_trgm при rollback сохраняется. Production provider recovery/ledger остаются отдельным контуром.

### ADR-042: широкие разделы каталога без автоматического разрешения форматов

Статус: принято для UX-TASK-042, 22.09.2026.

Контекст: покупателю нужен вход в обычный ассортимент цифрового marketplace, но ключи, подарки и типы аккаунтов требуют отдельной оценки и не должны смешиваться по названию игры.

Решение: добавить категории `games`, `software`, `game-assets` наряду с существующими направлениями. Категория описывает назначение товара и не меняет проверку `delivery_type`, идентичность варианта, модерацию или правила публикации. Отдельную категорию на каждую игру не создаём: нормализованное произведение и варианты хранятся в `catalog_works` и `products.identity_json`. До legal/payment review остаются прежние ограничения на ключи, подарки и аккаунты. Порядок разделов — гипотеза интерфейса, а не заявленная статистика продаж.

Последствия: миграция 000011 добавляет три записи в `product_categories` и меняет сортировку; обратная миграция требует сначала перенести опубликованные товары из удаляемых категорий. Поиск продолжает фильтровать строгий формат/регион/платформу и не объединяет несовместимые предложения.
