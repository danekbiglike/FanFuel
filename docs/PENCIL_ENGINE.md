Статус: технический прототип `0.1.0`, `UX-TASK-043`; **визуальный результат раннего анимационного рендера отклонён владельцем 23.09.2026**. **Текущий приоритет — контуры без заливки.** Стенд `http://127.0.0.1:5173/contour.html` показывает экспериментальный `renderPencilContours()` на прозрачном холсте. `PencilContourStroke` содержит путь, устойчивый `id`, кисть, необязательный `pressureProfile` и преобразование. Кисть содержит `widthCss` (ширина в экранных CSS px), `pigment` (RGB), `density`, `grain`, `tilt` и необязательный `fray` (0–1, удалённые боковые волокна). `PencilContourOptions` задаёт размер исходной сцены, размер отображения, DPR и seed. Координаты решётки, путей и поверхностей задаются в одной системе сцены. Привязку замкнутого силуэта и исходных осей делайте один раз при загрузке ассета, а в кадре деформируйте подготовленные точки и применяйте исходные `brush`/`pressureProfile` к новому пути. Поверхность с `bottom` — прямоугольная карточка с четырьмя гранями; без `bottom` — горизонтальная верхняя грань. `stepSoftBody` возвращает ID поверхности, нормаль, скорость и вид контакта (`soft`/`hard`). Подготовленный клип сильного приземления включается только после сильного удара сверху. В полёте движок сохраняет текущий наклон, на опоре постепенно выпрямляет корпус. Физика идёт фиксированным шагом 1/120 с; растеризация в покое запрашивается дважды в секунду, при движении — до 24 раз в секунду. Для движущегося персонажа задайте `grainSpace: "stroke"` и исходную `materialLengthCss` каждому штриху: фактура переезжает вместе с осью и растягивается с ней, а не остаётся сеткой пикселей холста. `boilFrame` меняет мелкое и среднее зерно дважды в секунду, `boilStrength` регулирует размах; при написании используйте фиксированный кадр. Пример полного цикла и ограничения описаны в [PENCIL_ENGINE_WEB_STAGE.md](PENCIL_ENGINE_WEB_STAGE.md). Стенд не является принятым рисунком персонажа или производительным actor runtime.

Реакции контакта в демо объединяются в короткий эпизод длительностью 750 мс, который продлевается каждым новым касанием. Внутри эпизода реакция может только повыситься по приоритету: мягкое касание края → мягкая опора → сильное касание края → сильный удар сверху. Отскок и повторное мягкое приземление не затирают сильный удар; после паузы начинается новый эпизод. Перетаскивание или перемещение стрелками сбрасывает состояние классификатора. Это UI-арбитраж реакций поверх физических событий, порог скорости `stepSoftBody` не меняет.

Детектор сдавливания работает в `stepSoftBody`: в пределах одного физического шага он собирает реально спроецированные контакты по нормалям. Пара противоположных нормалей («верх/низ» или «лево/право») считается зажимом только для разных ID поверхностей. Процент сжатия оценивается по текущей деформации и свободному зазору между гранями; упругие связи могут удерживать геометрию почти в исходной форме, поэтому одного измерения решётки недостаточно. `SoftBodyImpact.squeeze` несёт пару поверхностей, ось и оценку сжатия; `squeezeActive` не даёт повторять событие на каждом физическом шаге, пока Ойли зажат. Сжатие от 18 % классифицируется как сильное, а уже сильная скорость удара сохраняет свою классификацию при входе в зажим. В демо сдавливание выше обычных ударов в арбитраже и показывает обе поверхности; сильная реакция деформируется по оси давления.

Для общего адаптивного разбиения передавайте `createSoftBody(bounds, { maxSegmentLength: 28, maxSpringStretch: 1.45 })`: сетка выбирает от 5 до 9 узлов на ось так, чтобы её локальные связи были короче заданной длины. Числовая форма `createSoftBody(bounds, columns, rows)` сохраняет прежнюю сигнатуру и явное разрешение решётки. Каждая связь имеет свой предел растяжения относительно длины покоя; `setSoftBodyMaxSpringStretch(body, ratio)` задаёт его в диапазоне 1,05–2,5. Это не ограничивает общую длину растяжения тела: удлинение распределяется по цепочке локальных связей. На демо используется адаптивная сетка 28 CSS px и отношение 1,45. Захват мягкого тела сохраняет смещение указателя и плавно распределяет движение по соседним узлам.

При решении пружин закреплённый узел хвата считается неподвижной опорой: соседний свободный узел получает полную коррекцию связи. Если делить её пополам, а затем снова ставить точку хвата на курсор, ограничение можно обойти и слабое место смещается на соседнюю грань.

```ts
renderPencilContours(canvas, [{
  id: "edge",
  path: [{ op: "M", x: 10, y: 30 }, { op: "Q", cx: 60, cy: 0, x: 110, y: 30 }],
  pressureProfile: [0.65, 1.3, 0.78],
  taper: "both",
  brush: { widthCss: 4, pigment: [24, 24, 22], density: 0.85, grain: 0.35, tilt: 0.08, fray: 0 }
}], { sceneWidth: 120, sceneHeight: 60, cssWidth: 480, cssHeight: 240, dpr: 1, seed: 42 });
```

Для живого контура можно дополнительно передать `redrawFrame` и `redrawStrengthCss`. Первый параметр должен меняться только при новом показанном рисунке; второй задаёт небольшой поперечный сдвиг оси в экранных CSS px (0 отключает эффект, максимум 1,5). Отклонение плавное вдоль линии и замыкается на закрытом контуре, поэтому соседние точки не превращаются в шум. В стенде значение «Живость штриха» 60 % соответствует размаху 0,72 CSS px; в покое номер рисунка меняется дважды в секунду, при движении — на каждом показанном кадре до 24 раз/с. Бумажная фактура остаётся в материальных координатах штриха. Для анимации написания оставляйте `redrawStrengthCss: 0` и фиксированный `boilFrame`, чтобы уже созданный участок не дрожал.

Увеличение `cssWidth` в этом примере удлинит дугу, но базовая ширина останется около 4 CSS px. `pressureProfile` — значения нажима через равные доли длины пути; между ними используется плавная интерполяция без резких локальных провалов. Допустимый интервал значений — 0,55–1,4; некорректные числа заменяются на 1. Если профиль не задан, применяется медленное детерминированное изменение на масштабе всего жеста. Нажим влияет на ширину и тон, а не сдвигает ось. `taper` принимает `both` (по умолчанию для открытого пути), `start`, `end` или `none`: на концах ширина плавно уменьшается примерно на трёх базовых ширинах кисти, а в середине составного контура сужение можно отключить. Замкнутые пути не сужаются. Основной след складывается из трёх близких тонких волокон и контакта с бумагой. В образце `fray: 0`: дополнительные удалённые боковые волокна давали заметное двоение. Итоговая прозрачность слегка снижена, чтобы не получать предельно чёрный контур. Параметры и вид следа экспериментальные. `PencilContourBrush` дополнительно принимает `pressureScale` (общая сила), `pressureVariation` (размах авторского профиля), `randomness` (медленная детерминированная вариация), `taperLengthCss` и `taperMinimum`. Нулевая длина отключает сужение; значения по умолчанию сохраняют прежний вид. Для движущейся фигуры `grainSpace: "stroke"` строит бумажный контакт по координатам вдоль и поперёк штриха, чтобы фактура следовала за линией; `materialLengthCss` задаёт исходную длину до деформации. Мелкое и среднее зерно могут обновляться по `boilFrame`, а широкий рисунок контакта остаётся стабильным. Разглаживание контакта превращало след в серый маркер, поэтому в режиме движения сохранены разрывы и неодинаковая плотность графита. В контурном стенде можно выбрать наконечник из `.gbr` v2, `.vbr` 1.0/1.5, `.abr` v6 или ZIP с этими файлами. Переносится только маска наконечника. Порядок применения двух пользовательских архивов и запись пера описаны в [PENCIL_ENGINE_BRUSHES.md](PENCIL_ENGINE_BRUSHES.md). Стенд выполняет статичную генерацию в фоновом потоке при поддержке `OffscreenCanvas`; её время нельзя считать бюджетом анимационного кадра.

**Оптимизация контура после первого замера.** Рендерер обрабатывает только прямоугольник вокруг подготовленных путей, а цвет хранит в одном `ImageData` с отдельными буферами прозрачности и бумажного контакта. При 1000 CSS px/DPR 2 это около 2,0 млн рабочих пикселей вместо 4,0 млн; временные рабочие буферы занимают около 19 МБ вместо примерно 84 МБ в первой версии (без памяти самого canvas/bitmap и браузера). Расстояние между отпечатками увеличено с сохранением непрерывности следа. `contour.html` перестраивает рисунок в Web Worker через `OffscreenCanvas`, переносит готовый `ImageBitmap` на основной поток и объединяет быстрые изменения ползунков; при отсутствии API использует синхронный путь. Экран показывает отдельно время расчёта и задержку до показа.

Контрольный headless Chrome на этом ПК после прогрева: первая версия — около 66 мс на 1000 CSS px/DPR 2, обновлённая — около 36 мс. На 512 CSS px/DPR 2 обновлённый синхронный расчёт занимает около 16 мс. При эмуляции CPU ×4 он занимает порядка 63 и 175 мс соответственно для 512 и 1000 px: **перестраивать весь контур каждый анимационный кадр нельзя**. Для неизменного контура анимация должна использовать подготовленный слой, меняя только небольшую динамическую фактуру или геометрию изменившихся частей. Worker устраняет блокировку интерфейса при холодной сборке, но не уменьшает вычислительную работу. Эти числа не заменяют испытания на физическом слабом устройстве или в OBS.

**Текущая проба материала и сглаживания.** `smoothingCss` задаёт сглаживание деформированной оси в экранных CSS px: `0` отключает его, максимум `3`. Точки сначала расставляются равномерно вдоль линии, затем соседние усредняются с ограничением сдвига. У открытого штриха сохраняются концы, у замкнутого — стык. Ползунок «Сглаживание контура» в интерактивном стенде позволяет сравнить `0–3` CSS px; стартовые 70 % соответствуют `2,1` CSS px. В исходниках playground используется то же значение. Исходный ассет, физический коллайдер и независимая ширина грифеля не меняются. В режиме `grainSpace: "stroke"` контакт складывается из мелкого зерна и вытянутых вдоль жеста участков. Расход графита на отпечаток нормируется по исходной ширине кисти, чтобы сильный нажим повышал плотность и ширину следа; порог контакта с рельефом бумаги тоже зависит от нажима. Пресет интерактивного Ойли увеличивает размах авторского профиля до `pressureVariation: 1.55`, а для тонких линий лица уменьшает размах и усиливает контакт, чтобы глаза и улыбка не пропадали. Это художественная аппроксимация, не измеренная физическая модель.

**Стыки, углы и повторные проходы.** `PencilContourBrush.handwork` управляет короткими стыками жеста, выходами за острый угол и тонким повтором рядом с основным следом (`0` отключает эффект). На угловатых и открытых формах основной след пока лишь немного ослабевает, а поверх него появляется короткий второй след; для округлых петель используется разбиение самой линии, описанное ниже. Вероятность стыка выше у поворота, конца жеста и изменения нажима; вероятность повтора выше в середине длинного ровного участка. На резком углу иногда один, иногда два тонких жеста проходят на 1–3 CSS px дальше вершины, образуя небольшое перекрещивание. Места заново выбираются для каждого `redrawFrame`/`boilFrame` детерминированным seed и следуют за деформацией штриха. `handworkSide` при необходимости фиксирует сторону повтора. В стенде ползунок «Стыки и повторы» стартует с 50 %; повтор уже имеет при этом прежнюю силу 100 %, а большие значения усиливают стыки и угловые выходы. На глазах локально усилен стык, улыбка оставлена цельной. Настройка работает при `grainSpace: "stroke"` и `"paper"`; для письма с уже открытой линией следует оставить `handwork: 0` либо зафиксировать номер рисунка. Исходные пути и заливка не меняются.

**Округлые замкнутые контуры.** При `handwork > 0` для компактной округлой петли движок выбирает один стык. Компактность оценивается как `4π × площадь / периметр²` после деформации; текущий порог `0,86` отделяет глаза от каплевидного силуэта. В 96 % рисунков кандидат выбирается среди нижних 5 % высоты петли, в остальных допускается и другое положение. В короткой зоне основной отпечаток заменяется двумя концами того же контура: первый немного заходит за начало второго, оба сужаются, а графит коротко накапливается в перекрытии. Передача между концами распределяет суммарную плотность между двумя проходами: их общий вес ограничен, чтобы не возникал тёмный узел. Вспомогательный хвост рисуется одним тонким графитным волокном и ненадолго уходит внутрь петли; знак внутренней нормали определяется по направлению обхода контура. На каждом новом `redrawFrame` все замкнутые оси получают плавное низкочастотное отклонение: коэффициент `0,75 × widthCss × handwork` для округлых петель и `0,6 × widthCss × handwork` для остальных замкнутых форм, дополнительно с поправкой на длину. Это сближает абсолютный размах движения глаз и силуэта. Для округлой формы общий `redrawStrengthCss` дополнительно действует с коэффициентом 35 %, чтобы глаз оставался узнаваемым. Плавный профиль нажима привязан к `id`/seed штриха и не пульсирует каждый кадр. Короткий стык тоже получает новый вариант на каждом `redrawFrame`; зерно обновляется по `boilFrame`. Половины зоны соединения составляют около 6–9 CSS px каждая и ограничены 7 % периметра; фактическое наложение концов короче. На округлой петле дополнительный случайный повтор и угловые выходы отключены. Исходный путь и физический коллайдер не меняются; на остальных формах прежний механизм стыков пока сохраняется. У идеально правильного исходного вектора итоговая петля остаётся правильной: выраженную авторскую асимметрию нужно задавать исходным путём или записью пера, а не крупной случайной деформацией глаза. Порог и силу сверять на узких эллипсах, повёрнутых объектах и после сильной деформации: это художественная эвристика, а не распознавание сущностей.

## Быстрый запуск

Из корня репозитория:

```bash
npm run demo -w @fanfuel/pencil-engine
npm run test -w @fanfuel/pencil-engine
npm run typecheck -w @fanfuel/pencil-engine
npm run build:demo -w @fanfuel/pencil-engine
```

Адрес демо выводит Vite (обычно `http://127.0.0.1:5173/`). В нём доступны Ойли, написание `FAN`, пауза, масштаб 180–750 CSS px и светлая/тёмная темы интерфейса. Холст в обеих темах остаётся на светлой «бумаге», чтобы оценивать одну и ту же фактуру. Текст интерфейса хранится в `demo/locales.ts` для `ru/en`.

## Модель

Сцена хранит координаты, а не готовые пиксели. `PencilScene` содержит `width`, `height`, `seed`, `boilFps` и дерево `nodes`.

| Узел | Назначение |
| --- | --- |
| `shape` | Контур из `M`, `L`, `Q`, `C`, `Z`, цвет, толщина, зерно, заливка и штрихи. |
| `group` | Локальная система координат; вложенные группы образуют векторный скелет. |
| `sprite` | Набор векторных кадров, выбранных по `fps`; геометрия каждого кадра рисуется заново под текущий размер. |

`motion.keys` интерполируют перенос, поворот и масштаб. Вложение групп заменяет для прототипа отдельный solver костей. `reveal` открывает контур по длине за указанный интервал времени. `layoutPencilText()` собирает строку из авторских глифов, учитывает пробелы, переносы, трекинг и порядок штрихов. Заполненная фигура появляется после завершения контура; для эффекта постепенной заливки потребуется отдельная модель маски/штрихования.

Пример:

```ts
import { createPencilPlayer, type PencilScene } from "@fanfuel/pencil-engine";

const scene: PencilScene = {
  width: 200,
  height: 100,
  seed: 42,
  boilFps: 10,
  nodes: [{
    type: "shape",
    id: "signature-stroke",
    path: [{ op: "M", x: 10, y: 80 }, { op: "Q", cx: 80, cy: 0, x: 190, y: 50 }],
    style: { stroke: "#25251f", width: 3, grain: 0.8, temporal: "held" },
    reveal: { start: 0, end: 1.5 }
  }]
};

const player = createPencilPlayer(canvas, scene);
player.play();
// При снятии компонента: player.destroy();
```

Для React создавать player в `useEffect`, а в cleanup вызывать `destroy()`. На сервере `PencilRenderer` можно импортировать как тип/модуль, но `createPencilPlayer` требует DOM и вызывается только на клиенте. `PencilRenderer.draw(ctx, seconds, { width, height, dpr, reducedMotion })` подходит для собственного цикла или записи кадров.

## Как получается фактура

1. Кривые разбиваются методом де Кастельжо с допуском в экранных пикселях. Прямые и кривые повторно дискретизируются под текущий масштаб.
2. Контур рисуется несколькими прозрачными проходами разной ширины с небольшим отклонением и редкими графитовыми волокнами.
3. Заливка может содержать ограниченное числом коротких изогнутых штрихов поле `hatch`. Штрихи обрезаются исходным векторным контуром через Canvas clip.
4. `scene.seed` и `node.id` задают воспроизводимую фактуру. `temporal: "boil"` меняет её только в дискретные моменты `boilFps`; `held` сохраняет прежние штрихи. При `reveal` фактура всегда фиксируется, даже если указан `boil`.
5. Геометрия кривых и `Path2D` штрихов кэшируются по узлу, масштабу и кадру. Размер кэша ограничен. Векторные источники не зависят от DPR; холст перерисовывается под фактическое разрешение.

Прототип использует Canvas 2D. Это «векторный источник + адаптивная растеризация», а не бесконечно детализированный SVG: в любой момент экран остаётся пиксельным. Подход позволяет менять узор под масштаб без заранее подготовленных PNG. Для очень больших размеров потребуется отдельный budget на плотность штрихов и, возможно, тайловый/WebGL backend.

## Авторинг рисунка и надписей

- Рисовать несущий силуэт, глаза, реквизит и каждый смысловой слой отдельными замкнутыми или открытыми путями. Порядок узлов определяет порядок наложения.
- Для анимируемой части создать группу с локальным началом в шарнире. Потомки наследуют движение предка. Ключи движения задаются в секундах.
- Для смены формы кадр за кадром использовать `sprite.frames`; в кадрах хранить векторные узлы, не ссылки на PNG. Простые моргания или рот можно держать отдельным спрайтом поверх общего скелета.
- Надписи для эффекта написания должны состоять из отдельных **осевых линий штриха** в порядке написания с `reveal`. Демонстрационное `FAN` создано таким способом.
- `layoutPencilText(text, alphabet, options)` принимает `PencilAlphabet`: `unitsPerEm` и словарь `glyphs`, где каждый глиф содержит `advance` и массив путей `strokes`. Задайте `height`, `style`, а для написания — `start` и `secondsPerStroke`. Возвращается `group`, который можно вставить в сцену. Отсутствующий глиф вызывает ошибку, поэтому набор символов следует проверять при сборке ассета. API поддерживает кириллицу при наличии нарисованных глифов; тест включает букву `А`.
- Произвольный текст браузерного шрифта пока не превращается в карандашные штрихи автоматически. Следующая задача — офлайн конвертер контуров/скелетов глифов, полный набор `ru/en` и кернинг. `canvas.fillText` не даёт нужной модели штриха, поэтому не используется как обещание готовой функции.
- Не использовать `Math.random()` в рендере или общий seed для разных узлов. У каждого узла должен быть устойчивый уникальный `id`; при замене кадров геометрия кэшируется по объекту узла.

## Управление движением и производительность

- Player ограничивает вызовы отрисовки до 30 Гц; отдельное кипение — 10 Гц в демонстрации. Вне viewport и в скрытой вкладке цикл приостанавливается.
- `prefers-reduced-motion` и Save-Data показывают статичный кадр. При уменьшенном движении `reveal` полностью открыт.
- DPR ограничен `2` в player. Для небольших стикеров размер исходной сцены не обязан совпадать с размерами canvas.
- Проверять разные сценарии отдельно: маленький стикер, несколько одновременно, 750 px при DPR 2, виджет OBS, слабый телефон. Целевой budget до интеграции: не более 4 мс CPU на кадр одного 512 px персонажа на среднем мобильном устройстве, без заметных long tasks, с контролем памяти кэша. Это **критерий для будущей проверки**, не подтверждённая характеристика.
- Первичный замер в headless Chrome на рабочем ПК: среднее время 80 последовательных `draw()` после прогрева — 0,83 мс при 180 px, 1,43 мс при 512 px и 1,72 мс при 750 px, DPR 2. Он не включает полноценный замер compositor/GPU, длительный сеанс и слабые устройства; сравнение со стикерами Telegram пока не обосновано.

## Дальнейшая разработка

1. Согласовать эталонный набор: 3–5 авторских векторных сцен из разных типов штриха, в том числе детальный Ойли, письмо кириллицей и светлую/тёмную подложку. Подобрать зерно и контраст по скриншотам при 64/180/512/1000 px; добавить визуальные регрессионные эталоны.
2. Создать офлайн CLI импорта ограниченного SVG subset и авторинг-формат с валидацией геометрии, лимитами размера и версионированием. Не исполнять произвольные SVG-скрипты/ссылки и не принимать CSS-фильтры без проверки.
3. Добавить глифы с осевыми штрихами, ручной кернинг и раскладку `ru/en`; отдельно проработать заливки глифов и порядок написания.
4. Добавить rig editor/экспорт: шарниры, pivot, деформацию путей, easing и смешивание поз. Уточнить разницу между спрайтовой подменой формы и скелетным движением.
5. Профилировать пачку стикеров и OBS на слабом телефоне. При необходимости внедрить Worker/OffscreenCanvas, предварительную растеризацию неподвижных слоёв или WebGL backend, сохранив общий формат сцены.
6. Провести character/design review и ограниченный UI-пилот по `UX-TASK-038`. После согласования и performance QA отдельно решать, заменяет ли движок текущий WebP/SVG-слой Ойли. До этого production-страницы не меняются.

Платежи, API, БД и новые пользовательские страницы эта задача не затрагивает.
